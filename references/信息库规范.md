# 信息库规范 v1.0

> 配套：`排版规则.md`、`微调细则.md`
> 定位：信息库是**唯一事实来源**。简历、网申表单、面试话术，全部从它派生。

---

## 零、为什么要有信息库

用户给的是一份简历，简历是"给 HR 看的视图"，不是事实本身。它缺字段（学院、籍贯、身高体重）、有压缩（一段实习三个 bullet）、还可能带错（解析错位、口径不一、编辑残留）。

信息库要做的是：**把简历拆成一条条可核验的事实，逐条和用户确认，确认过的才是真的。** 之后所有产出都以它为准，不再回头翻原始简历。

一旦信息库锁了，简历只是它的一种排版输出。

## 一、目录结构

```
用户/
├── profile.json        静态档案（联系方式、身份信息、求职偏好）
├── experience.json     经历库（教育 / 实习 / 项目 / 校园 / 技能 / 奖项）
├── confirm-log.md      逐条确认记录（谁什么时候确认了什么）
└── assets/
    └── photo.jpg       证件照（白底，≥300dpi）
```

**所有文件存本地，不随仓库分发。** `.gitignore` 里必须排掉。

## 二、经历库的数据结构

每条经历是一个对象：

```json
{
  "id": "exp_001",
  "type": "internship",
  "org": "某办公软件公司",
  "role": "渠道运营实习生",
  "start": "2026.07",
  "end": "2026.10",
  "ongoing": false,
  "location": "深圳",
  "headline": "负责某设计工具国内+海外双版本推荐位运营",
  "bullets": [
    {
      "theme": "AI 内部提效",
      "action": "基于 Codex 搭建两款 AI 工具",
      "method": "自动定价核验、模板翻译校验",
      "result": "被团队采纳为标准，回测节省 80% 审核工时，准确率 95%",
      "metrics": ["80%", "95%"],
      "evidence": "配置已开源至 GitHub"
    }
  ],
  "metrics_all": ["80%", "95%", "20%", "10+"],
  "status": "confirmed",
  "confirmed_at": "2026-10-30T15:20:00+08:00"
}
```

**关键设计**：

- `theme`：每条 bullet 的加粗小标题，四到六字，是这条信息的检索标签
- `metrics`：该 bullet 内的所有数字，单独成数组，用于口径校验
- `metrics_all`：整条经历的数字汇总，用于跨版本比对
- `status`：`draft` / `confirming` / `confirmed` / `deprecated`

## 三、逐条确认机制（本规范的核心）

### 3.1 铁律：不许批量确认

**一次只确认一条经历。** 整份简历一次性丢给用户说"你看看对不对"，用户会扫一眼说"差不多"，然后数字错误一路带到面试现场。

### 3.2 呈现格式（固定，不许自由发挥）

每条经历的确认卡片包含四块：

```
【第 2 条 / 共 5 条】实习经历

原文：
某办公软件公司  渠道运营实习生  2026.07-2026.10
● AI 内部提效：……

拆解：
· 组织：某办公软件公司
· 角色：渠道运营实习生
· 时间：2026.07 - 2026.10（不在职）
· 动作 1：基于 Codex 搭建两款 AI 工具
  方法：自动定价核验、模板翻译校验
  结果：被采纳为标准，省 80% 审核工时，准确率 95%

需要你确认三件事：
1. 起止时间对不对？现在还在职吗？
2. 上面的描述有没有夸大，或者漏掉了你做过的事？
3. 数字逐个核：80%、95% —— 都对吗？
```

### 3.3 三个必问问题

1. **时间**：起止对不对，是否在职（决定简历写"至今"还是写结束月份）
2. **描述**：有没有夸大，有没有漏掉的重要工作
3. **数字**：逐个念，逐个确认

### 3.4 用户的三种回应

| 回应 | 处理 |
|---|---|
| 确认无误 | `status = confirmed`，写 confirm-log，进入下一条 |
| 有错要改 | 当场改，改完**重新完整呈现一次**再确认（不能"改一个字就当确认过了"） |
| 这条不要了 | `status = deprecated`，不删记录（留痕），从简历视图里移除 |

### 3.5 顺序

教育 → 实习（按时间倒序）→ 项目 → 校园 → 技能与奖项。

理由：从最不可能出错的开始，让用户熟悉确认节奏，再到最容易有争议的经历描述。

## 四、数字核对协议

数字是简历上最值钱也最危险的东西。协议如下：

1. **每个数字单独念**，不合并成一句"80%、95%、20% 都对吗"
2. 用户必须对**每一个**数字明确回答（对 / 不对 / 不确定）
3. 出现"不确定"的，标记 `needs_evidence`，让用户回去查原始记录，不许猜
4. **同一指标出现两个值**（如"1000+ 次数据更新"与"3600+ 次操作"并存），必须停下来问，不许自行取舍
5. 所有数字录入 `metrics` 数组，后续每份简历导出前自动比对，任何一个对不上就报警

## 五、B 类：简历没有、网申必填

这些必须在建档阶段问完，否则每次投递都会卡住。

**身份类**：性别、出生日期（年月日）、证件类型、证件号码、政治面貌、籍贯（省/市）、身高、体重、是否统招、应届/往届、毕业时间（年月）

**教育类**：本科与硕士各自的**学院名称**（简历普遍不写，网申几乎都问）、是否全日制、是否第一学历

**联系方式**：手机、邮箱、现居城市、紧急联系人（部分公司要）

**其他**：英语等级与分数、是否有亲属在本公司任职

> 注意：这些信息只存本地 `profile.json`，不进仓库、不进对话记录之外的任何地方。

---

## 六、C 类：每次投递才决定

期望城市、期望行业、期望职业、现月薪、期望月薪、到岗时间、内推码、志愿顺序。

首次建档时问一轮作为默认值，之后每次投递只确认是否沿用。

## 七、状态机

```
draft ──→ confirming ──→ confirmed ──→ locked
                ↑            │
                └────────────┘（发现错误，回退重确认）
```

- **`locked` 之后修改需要用户显式提出**，且修改必须留痕：记录改了什么、什么时候改的、为什么改。
- 全部经历 `confirmed` 之后才能 `lock`，才能进入投递流程。
- 存在任何 `draft` 或 `confirming` 状态的条目，**不允许开始投递**。

---

## 八、信息库与简历的关系

**简历是信息库的一个视图，不是事实来源。**

- 微调简历时，只能改表述，不能改 `experience.json` 里的事实
- 信息库更新后，**已投递的简历不追溯**（那是历史快照），新简历用新事实
- 每份派生简历记录 `derived_from: exp_version`，便于追溯口径

---

## 九、入库校验（缺一不可）

| # | 校验项 | 标准 |
|---|---|---|
| 1 | 每条经历至少 2 条 bullet | 少于 2 条的，问用户是不是漏了 |
| 2 | 每条 bullet 至少有 1 个数字 | 确实没有的，标 `no_metric` 并写原因 |
| 3 | 所有数字进入 `metrics` | 无遗漏 |
| 4 | 无重复指标不同值 | 有冲突即中断 |
| 5 | 时间区间连续无空洞 | 有空洞（如半年空白）要问清 |
| 6 | 无 `draft` / `confirming` 残留 | 全部 `confirmed` 才可锁 |
| 7 | 已写 confirm-log | 每条都有时间戳 |

---

## 十、用户不愿意逐条确认怎么办

先说明风险：数字错到面试现场是最难看的，而且没法当场改。

用户仍坚持跳过 → 标记 `status = skipped`，并在**每一份**派生的简历交付时附一句提示：「本简历未经逐条确认，数字与描述请自行复核」。不许默默放过。
