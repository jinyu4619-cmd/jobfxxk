# 投递台账规范 v1.0

> 触发：**每次投递成功之后**自动生成或更新
> 定位：投递进度是用户最关心的东西。投了哪家、到哪一步、还来不来得及，一眼要能看清

---

## 一、什么时候写

| 时机 | 动作 |
|---|---|
| 投递前 | 写一条「待投递」草稿，记录目标岗位与简历版本 |
| **用户点提交、系统返回成功页** | 状态改为「已投递」，补齐投递日期、入口链接、内推码来源 |
| 提交失败（校验不过、被拦截、超时） | **不写入台账**，记录失败原因，交由用户重试 |
| 收到测评/笔试邀请 | 状态改为「测评/笔试」，补测评截止日 |
| 收到面试邀请 | 状态改为「面试中」，同时在面试台账里开一条 |
| 收到拒信 / 流程终止 | 状态改为「已终止」，记终止日期与阶段 |
| 拿到 offer | 状态改为「offer」 |

**判定"投递成功"的唯一标准**：系统页面明确出现成功提示，或投递记录里能查到这条申请。**看到提交按钮变灰、页面跳转，都不算成功**，必须以能查到的记录为准。

---

## 二、存储

双份，同源：

- `投递台账.md`——给人看的表格，用户随时打开
- `投递台账.json`——给程序读的结构化数据

两份由同一个数据源生成，**不允许只改一份**。

---

## 三、字段定义

### 3.1 主表（投递）

| 字段 | 必填 | 说明 |
|---|---|---|
| 序号 | 是 | 自增，不重用 |
| 公司 | 是 | 全称 |
| 岗位全称 | 是 | 系统里的原始名称，不改写 |
| 批次 | 否 | 提前批 / 正式批 / 补录 |
| 城市 | 是 | 工作地点 |
| 匹配度 | 否 | 推荐阶段的打分，0–100 |
| 志愿顺序 | 否 | 第一/第二/第三志愿 |
| 投递日期 | 是 | YYYY-MM-DD |
| 投递方式 | 是 | 网申 / 邮箱 / 线下双选会 / 内推 |
| 入口链接 | 是 | 实际投递的页面地址 |
| 简历版本 | 是 | 文件名，如「张三 27秋招 - 某消费品公司.pdf」 |
| 内推码 | 否 | 实际填入的码 |
| 内推码来源 | 否 | 用户提供 / 飞书表 / 未使用 |
| 截止日期 | 否 | 该岗位投递截止 |
| 测评截止 | 否 | 收到邀请后补 |
| 状态 | 是 | 见第四节 |
| 最近更新 | 是 | 每次改动都要动这个字段 |
| 下一步 | 是 | 一句话，如「等测评通知」「10-30 前完成测评」 |
| 备注 | 否 | 异常情况记录 |

### 3.2 派生统计（自动计算，不手填）

- 累计投递数
- 在流程中数（已投递及之后、未终止）
- 已终止数
- offer 数
- 面试转化率 = 进面数 ÷ 已投递数
- 待办提醒：7 天内到期的测评 / 截止日期

---

## 四、状态机

```
待投递 → 已投递 → 筛选中 → 测评/笔试 → 面试中 → offer
                     ↘         ↘          ↘
                      已终止   已终止     已终止
```

规则：

- **只能向前推进**，不能回退（写错了改备注，不改状态）
- 每个状态变更必须带日期
- 「已终止」是终态，之后不再更新

---

## 五、与面试台账的分工

沿用已有约定：**投递流程记这张表，面试逐场记另一张表。**

- 投递台账：只管到"进了面试"这一步，记公司、岗位、时间
- 面试台账：记录每一场的轮次、形式、结果、评级、复盘要点

两张表通过「公司 + 岗位」关联，不重复记同一件事。

## 六、生成格式（Markdown 部分）

```markdown
# 投递台账

> 最后更新：2026-10-30 ｜ 累计投递 81 ｜ 在流程中 64 ｜ 已终止 17 ｜ offer 0

## 一、待办提醒

| 事项 | 截止 | 剩余 |
|---|---|---|
| 某某公司 测评 | 2026-11-02 | 3 天 |

## 二、在流程中

| # | 公司 | 岗位 | 城市 | 投递日期 | 状态 | 下一步 |
|---|---|---|---|---|---|---|

## 三、已终止

| # | 公司 | 岗位 | 终止阶段 | 终止日期 |
|---|---|---|---|---|
```

**排序**：在流程中的按「下一步的紧急程度」排，到期的在前；已终止的按日期倒序。

## 七、写入纪律

1. **只记录事实**，不写推测（"感觉能过"不写）
2. **一处改动，两处同步**（md 与 json）
3. **每次投递只写一行**，重复投同一岗位要新建一行并标注"二次投递"
4. **失败不记账**：提交没成功的，不进主表，进「失败记录」附注，避免污染统计
5. 用户手动改过的行，程序不覆盖，只在备注里追加

---

## 八、交付给用户的内容

每次投递完成后，**只交付两样**：

1. **更新后的投递进度**（新增的那一行 + 更新后的统计）
2. **状态如实标注**——用户提供了后续进展（测评邀请、面试时间、已拒等）就按实际写；**没提供就写「已投递」这个初始状态，不推测、不预设**

**不做的事**：不主动推荐下一家。

投完一家就往上推下一家，是在替用户做决定。用户没说要继续，这个环节就结束。

### 8.1 何时才推荐下一家

必须先问一句，得到肯定答复才推荐：

> 「还打算继续投吗？」

- 用户说继续 → 才给下一家建议（按匹配度），并且只给 1 个，不给清单
- 用户说不投了 / 没回应 / 只回了个表情 → **停止，不再提推荐的事**
- 用户说先歇一歇 → 记录状态，不再主动跟进

**同一次对话里，被拒绝过一次就不再问第二次。**

## 九、异常处理

| 异常 | 处理 |
|---|---|
| 提交后页面报错但无明确提示 | 去投递记录页确认是否已生成申请；确认不到则判定失败 |
| 投递成功但入口链接失效 | 记公司+岗位，链接留空并备注 |
| 同一岗位重复投递 | 新建行，备注「二次投递，原记录 #N」 |
| 用户投完又撤回 | 状态改「已终止」，备注「本人撤回」 |
| 测评邀请邮件未收到 | 记录「已投递，待测评邀请」，7 天后提醒用户查邮箱/垃圾箱 |
