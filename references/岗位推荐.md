# 岗位推荐细则 v1.0

> 触发：用户没给岗位、没给公司，或只给了其中之一
> 数据源：飞书多维表格「27秋招汇总表」（实时更新，约 3000 条）

---

## 一、四种情形与对应策略

| 用户给了什么 | 处理 |
|---|---|
| 公司 + 岗位 | 跳过推荐，直接进筛岗校验（确认该岗还在招、门槛是否满足） |
| 只有公司 | 从表里捞出该公司全部在招岗位 → 与信息库匹配 → 推荐 1–3 个具体岗位 |
| 只有岗位方向（如"想做用户运营"） | 按方向 + 城市 + 届次 + 学历筛 → 匹配打分 → 出 5–8 家公司 |
| 都没有 | **先问三个问题**，不直接推荐 |

### 1.1 都没给时先问的三个问题

1. 想在哪些城市？（可多选，「不限」也算答案）
2. 有没有偏好的行业？（消费品 / 互联网 / 制造 / 金融 / 不限）
3. 岗位方向有没有倾向？（运营 / 产品 / 市场 / 数据 / 管培 / 不限）

三个都不答，就按信息库里的默认意向走，并明确告知「以下推荐基于你档案里的默认意向」。

---

## 二、数据源

### 2.1 主数据源：飞书表「27秋招汇总表」

已实测可读，字段如下：

`企业名称`｜`岗位列表`｜`所属行业`｜`工作城市`｜`学历要求`｜`届次要求`｜`招聘类型`｜`企业类型`｜`开始日期`｜`截止日期`｜`公告地址`｜`投递地址`｜`独家标签`｜`独家情报（仅供参考）`｜`更新日期`｜`倒计时`｜`url_md5`

**读取方式**：用户已登录飞书网页版的前提下，拦截页面自身的数据接口，返回体是 gzip + base64，本地解压后按 `recordMap` 还原成行。不依赖飞书开放平台应用，不需要 App ID。

**已知限制**：子表切换需要逐个抓取，一次只能稳定拿一张表。抓取时按子表分文件落盘，不要试图一次抓完。

### 2.2 兜底数据源

表里没覆盖的公司或行业，回退到官网直接扫（读岗位列表接口或页面）。**不做全网爬取**——噪音太大，且很多岗位信息过期。

### 2.3 数据新鲜度

- `更新日期` 超过 30 天的，标注「信息可能过期」，不直接推荐
- `截止日期` 为「招满即止」的，按 `开始日期` 距今超过 60 天视为高风险，提示用户先自行确认
- 有明确 `截止日期` 且已过的，直接剔除

---

## 三、硬门槛过滤（先筛掉，再打分）

按顺序过四道，只要一道不过就剔除，不进入打分：

1. **届次**：`届次要求` 必须包含用户毕业年份（2027 届）
2. **学历**：`学历要求` 必须覆盖用户最高学历（硕士）
3. **城市**：用户指定城市时，`工作城市` 需命中；用户说不限则跳过
4. **岗位线**：`岗位列表` 与用户意向方向有交集

过滤后若剩余 0 条，不要硬凑，直接告诉用户「表里没有符合条件的，建议放宽哪一条」，并给出放宽后的结果。

---

## 四、匹配打分（满分 100）

| 维度 | 分值 | 判据 |
|---|---|---|
| 经历同构度 | 40 | 岗位职责与信息库里已确认的经历有可直接对应的动作 |
| 能力要求重合 | 30 | JD 要求的技能/工具，用户已具备的比例 |
| 加分项 | 20 | 用户独有优势的命中（如出海经历、AI 工具、数据背景） |
| 偏好匹配 | 10 | 城市、行业与用户偏好一致 |

**同分时的排序**：截止日期近的优先（还有窗口的），其次是公司规模/知名度。

**岗位名称不参与打分。** 同一件事在不同公司叫法完全不同，「ToC 渠道运营」「用户增长」「线上运营」可能指向同一类工作。打分只看**职责描述与已确认经历能不能对上**，不看名字像不像。

代价是可能推出名字看起来不相关的岗位，补偿办法见 10.7 第三条。

---

## 五、输出格式（只给 3–5 个）

**排序规则：全表按匹配度降序，不按城市分组、不按公司分组、不做批次合并。** 同一家公司的提前批和正式批各占一行。

**每行必须标注**：公司、精确岗位名、批次、城市——这四项缺一项，用户就没法判断要不要投。

不给全量清单。每个推荐项固定六行：

```
【第 1 推荐】××公司 · 用户运营管培生
匹配度 86 / 100
为什么推：你的某办公软件公司分层实验和这个岗的"用户生命周期运营"直接对应
硬门槛：2027 届 ✅｜硕士 ✅｜杭州 ✅
时效：截止 2026-11-30，还有 31 天
入口：直投链接（已存到投递台账）
```

**必须说明的三件事**：为什么匹配（要指到具体经历）、有没有硬伤、还来不来得及。

## 六、内推码：优先级与流程

### 6.1 三级优先

1. **用户自己的码** —— 直接用
2. **飞书表「内推码分享」子表** —— 用户没有时来这里查
3. **不填** —— 两处都没有就留空

### 6.2 标准流程（按顺序，不许跳）

```
① 这家的网申表里有「推荐码 / 内推码」字段吗？
   └─ 没有 → 结束，不用管
② 问用户：「你有这家的内推码吗？」
   ├─ 有 → 填入，记录来源=用户
   └─ 没有 → 进 ③
③ 去飞书「内推码分享」表里按公司名查
   ├─ 查到 → 把码和来源一起给用户看，**用户确认后再填**
   └─ 查不到 → 留空，告诉用户"这家表里没有内推码"
```

### 6.3 为什么不再上网搜

之前试过在小红书检索，结论是：笔记正文有网页端拦截，码基本是上一届发的，跨届大概率失效，而且北森这类系统对无效码是**静默忽略**——填了也不会有任何反馈。飞书表里的码由人工维护、带更新日期，可靠性高一个量级。

**除非用户明确要求去搜，否则不启用浏览器检索。**

### 6.4 填入前必须做的事

- 把码和它的来源一起念给用户：「表里查到 XX 的码是 C64Z1，来源是飞书表，要填吗」
- 用户确认后才填
- 填入后记录到投递台账，标注来源

---

## 七、用户否决推荐怎么办

用户说「这些都不投」时：

1. 不追问理由，先问一句「是方向不对，还是公司不对」
2. 记录到偏好档案，后续推荐避开
3. 允许用户直接给公司名或链接，跳过推荐环节

**不许反复推荐被否决过的公司。**

---

## 八、推荐与投递的衔接

用户选定后，进入标准流程：定志愿顺序 → 挑底稿 → 微调 → 上传 → 填表 → 核对 → 用户提交。

推荐阶段产出的信息要落到投递台账：公司、岗位、投递入口、截止日期、匹配度、内推码来源。

---

## 九、当前能力边界（如实写清）

- 飞书表读取**依赖用户已登录飞书网页版**；未登录时提示用户先登录，插件不做扫码
- 子表需逐个抓取，单次运行只保证一张表
- 表里若出现新的公式字段或富文本链接，解析可能失败，失败时跳过该字段而不是整行丢弃
- 3000 行规模下，推荐打分在本地完成，不上传任何数据

## 十、意向获取完整路径

这一节把"从不知道自己想投什么"到"在浏览器里打开投递官网"的全程画完。

### 10.1 主决策树

```
【入口】需要确定「目标公司 + 目标岗位」

├─ 用户已给出「公司 + 岗位」
│   └─ 直接进 10.5 打开官网
│      （中途校验：岗位是否仍开放、门槛是否满足）
│
├─ 用户只给「公司」
│   ├─ 该公司在飞书表里 → 取该公司全部在招校招岗 → 与信息库匹配 → 推荐 1–3 个
│   ├─ 不在表里 → 联网查该公司校招官网 → 取岗位列表
│   └─ 查不到 → 告知用户，请其提供岗位名或链接
│
├─ 用户只给「方向」（如"想做用户运营"）
│   └─ 进入 10.2 数据源选择
│
└─ 「公司和方向都没给」
    └─ 先问三问（城市 / 行业 / 方向）→ 进入 10.2 数据源选择
```

### 10.2 数据源选择（按优先级，逐级降级）

```
① 用户自带清单
   （文件、表格、链接、口述的公司名）
   └─ 有 → 直接解析，不碰其他数据源
   └─ 没有 → ②

② 飞书多维表格
   └─ 登录态存在且表可读 → 读取并推荐
   └─ 未登录 → 进 10.3 登录引导
   └─ 用户拒绝 / 登录失败 / 无权限 → ④

③ （②失败后的分支，见 10.3）

④ 用户自行提供
   └─ 用户愿意自己给公司名 → 回到「只给公司」分支
   └─ 用户不愿意 → ⑤

⑤ 联网搜索（兜底）
   └─ 用户没给意向公司，且仍需要推荐 → 执行 10.4

⑥ 全部不可用
   └─ 明确告知无法继续，不编造岗位
```

### 10.3 飞书登录引导（必须先说明，后请求授权）

**顺序不能颠倒：先讲清为什么，再问同不同意，最后才打开登录页。**

**第一步 · 说明（原文照用）**

> 我需要读一张公开维护的校招岗位表（约 3000 条，实时更新），用来给你的经历做匹配。
> 这张表在飞书上，读取需要你登录。
>
> 登录后我只会读这一张表的内容：企业名称、岗位列表、学历要求、城市、截止时间、投递地址等岗位字段。
> 我不会读你的其他云文档、聊天记录、通讯录，也不会把你的信息写到表里。
> 读到的岗位数据只在本地匹配，不外传。
>
> 你愿意登录吗？

**第二步 · 用户三选一**

| 回应 | 动作 |
|---|---|
| 同意 | 打开飞书登录页 → 用户扫码 → 检测登录态 → 读表 |
| 拒绝 | 不打开登录页，直接降级到 ④ |
| 想用但自己来 | 引导用户自己打开飞书、登录、进入表格，登录完成后通知我继续 |

**第三步 · 登录后的校验**

- 检测是否真的登录（读取页面上的用户信息或直接试读接口）
- 试读一次表结构，确认有权限
- 读不到（无权限 / 不是组织成员 / 表已迁移）→ 归入「登录失败」，降级到 ④，并说明失败原因

**第四步 · 随时可撤回**

用户中途反悔，立即停止读取，删除已落盘的临时岗位数据。

### 10.4 联网搜索（兜底，规则要严）

**允许的前提**（三条全满足才执行）：
1. 用户没提供意向公司
2. 飞书路径不可用（拒绝 / 失败 / 无权限）
3. 用户明确要求"你帮我找"

**搜索方式**

- 关键词组合来自信息库：岗位方向 + 城市 + 届次（如「2027 届 用户运营 校园招聘 杭州」）
- **只发岗位关键词，不发任何个人信息**——不把简历内容拼进搜索词
- 优先来源：公司校招官网 › 高校就业信息网 › 公开校招聚合站
- 每个结果必须记录：来源链接、抓取时间、是否官方域名

**结果校验（不合格一律不推荐）**

| 校验项 | 标准 |
|---|---|
| 时效 | 页面明确标注的截止日期已过的，剔除；无标注且发布日期超 60 天，标注高风险 |
| 届次 | 明确写 2027 届或"2026.8–2027.7 毕业"；写 2026 届的直接剔除 |
| 官方性 | 域名属于该公司官方或正规招聘系统（北森、Moka、飞书招聘、Workday 等） |
| 可投递 | 有明确的投递入口，不是只有一篇公告 |

**关于"山寨链接"**：搜索结果的链接要先打开确认是招聘系统页面，再交给用户。跳转到无关页面、要求下载 App、或域名可疑的，一律不推荐并说明原因。

### 10.5 打开投递官网

**入口优先级**

1. 飞书表里的「投递地址」（直投链接）
2. 公告页里的网申入口
3. 官网 → 人才招聘 → 校园招聘 → 目标岗位

**打开后的判断**

- 落到岗位列表页 → 定位目标岗位 → 点「立即投递」
- 落到登录页（微信扫码 / 账号）→ **停下来让用户登录**，登录后再继续
- 落到 404 / 岗位已下线 → 回退到上一层重新找，不硬闯

**打开前必须告知用户**：这是哪家公司的哪个岗位，链接来自哪里（飞书表 / 官网 / 搜索），确认后再打开。

### 10.6 覆盖度自检

| 情形 | 是否覆盖 | 处理 |
|---|---|---|
| 公司+岗位都给 | ✅ | 校验后直接开官网 |
| 只给公司，表里有 | ✅ | 取该公司岗位再推荐 |
| 只给公司，表里没有 | ✅ | 联网查该公司校招官网 |
| 只给方向 | ✅ | 走数据源树 |
| 都没给 | ✅ | 先问三问再走树 |
| 飞书未登录 | ✅ | 说明→请求授权→扫码 |
| 用户拒绝登录 | ✅ | 降级到自带清单 / 自行提供 / 联网 |
| 登录成功但无表权限 | ✅ | 归为登录失败，降级 |
| 用户中途反悔 | ✅ | 停止读取，删除临时数据 |
| 搜索到的岗位已截止 | ✅ | 剔除并说明 |
| 搜索到山寨或无关链接 | ✅ | 不推荐，说明原因 |
| 用户什么都不提供也不同意联网 | ✅ | 明确终止，不编造 |
| 同一公司多个批次（提前批/正式批） | ✅ | 各占一行，全部列出，不合并 |
| 用户想投多个城市 / 多个岗位 | ✅ | 混排，只按匹配度降序，不按城市分组 |
| 岗位名与用户叫法不一致 | ✅ | 按经历语义匹配，不按字面匹配 |
| 用户什么都不提供 | ✅ | 直接告知无法协助，不推荐、不编造 |

### 10.7 已定口径

**一、同公司多批次：按岗位列，两条都列。**
同一家公司的提前批和正式批是两条独立的岗位记录，各自有截止时间和投递入口，合并会丢掉信息。各占一行，分别标注批次。

**二、多城市 / 多岗位：只按匹配度排序。**
不按城市分组，不按公司分组。原因是分组会让用户以为某一组更优先，而实际决策依据只有匹配度。每条结果里标明城市和批次，让用户在排序结果里自行取舍。

**三、岗位名口径：以经历匹配度优先。**
不同公司对同一种活有不同叫法——「ToC 渠道运营」「用户增长」「线上运营」在有的公司是同一件事。所以**岗位名称不参与打分，也不作硬性筛选条件**，唯一判据是这份经历能不能对上这份职责。

代价是可能推出名字看起来不相关的岗位，补偿办法：**每条推荐必须写一句「为什么这个岗位名不叫 X，但实际做的是 X」**，把对应关系摊开给用户看，让他自己判断。

**四、什么都不提供：直接告知无法协助。**
用户既不给方向、也不给公司、也不同意登录、也不让联网——这不是真想投简历，是在试探。此时明确说明「没有岗位方向我无法给出有意义的推荐」，结束这个环节，不硬凑、不编造。
