# 网申问题库 v1.0

> 用途：在生成简历**之前**，把网申系统会问的字段一次性问完
> 来源：某消费品公司 2027 校招（北森）真实表单倒推 + 常见校招系统字段
> 原则：**问题库只增不减**。每遇到一个新字段，追加进来，下次自动复用

---

## 零、为什么要提前问

网申系统的字段高度同质化。北森、Moka、飞书招聘、用友、Workday 换汤不换药，来回就是那三十几个字段。

但这些字段里，**简历上有的不到一半**。学院名称、籍贯、身高体重、是否统招、应届往届、毕业时间精确到月、证件号码——简历里统统没有，可系统全要。

不提前问，就会在投递现场一边翻资料一边填，填错一个数字就得重来。所以顺序必须是：**收经历 → 逐条确认 → 问问题库 → 锁档案 → 出简历**。简历在最后，因为它要按岗位方向取舍内容，而岗位方向来自问题库里的「期望职业」。

## 一、采集顺序与时机

```
1. 收经历，逐条确认          （见《信息库规范》第三节）
2. 跑一遍本问题库            ← 你在这里
3. 锁定档案 profile.json
4. 生成简历两版本（docx + pdf）
5. 筛岗、投递、填表
```

**第 2 步没走完，不许进第 4 步。**

## 八、内推码的特殊处理

### 8.1 两级来源，顺序固定

1. **用户自己的码**（在职员工、校园大使、宣讲会）——直接用
2. **飞书多维表格「内推码分享」子表**——用户没有时来这里查
3. 两处都没有 → **留空**

### 8.2 标准流程

```
① 这家表单里有「推荐码 / 内推码」字段吗？
   └─ 没有 → 结束
② 问用户：「你有这家的内推码吗？」
   ├─ 有 → 填入，标注来源=用户
   └─ 没有 → 进 ③
③ 去飞书「内推码分享」表按公司名查
   ├─ 查到 → 把码和来源给用户看，确认后再填
   └─ 查不到 → 留空，明确告知"这家表里没有"
```

### 8.3 不做的事

**不再上网搜内推码。** 实测结论：小红书等平台对笔记详情有网页端拦截；流传的码多为上一届所发，跨届失效；北森这类系统对无效码**静默忽略**，填了没有任何反馈，反而掩盖问题。

飞书表由人工维护、带更新日期，可靠性高一个量级。

**除非用户明确要求，否则不启用浏览器检索内推码。**

### 8.4 填入前

把码和来源一起念给用户确认，填入后记录到投递台账并标注来源。

## 九、隐私分级与代填协议

### 9.1 三级分类

| 级别 | 包含 | 默认处理 |
|---|---|---|
| **P0 极敏感** | 证件号码、银行卡号、紧急联系人电话、家庭住址、家庭主要成员信息 | **默认不代填** |
| **P1 敏感** | 身高、体重、籍贯、政治面貌、婚育状况、户口与档案所在地 | 需显式授权才代填 |
| **P2 常规** | 姓名、性别、出生日期、手机、邮箱、学校、专业、学院、时间、期望意向 | 正常代填 |

### 9.2 建档时必须问的一句

> 「身份证号、紧急联系人这类信息，你希望我怎么处理？三个选项：
> **A. 全部由我代填**（存在你本地，不进仓库、不进日志）
> **B. 我只填 P2，P0/P1 每次你自己输**（推荐）
> **C. 全部你自己填**」

### 9.3 三种选择的差异

**选 A**：值存本地 `profile.json`，明文。填表时通过环境变量传给脚本，不写进任何脚本文件、不写进 confirm-log、不写进 Git。需明确告知：值会经过一次进程传参，本地临时文件里可能短暂出现。

**选 B（推荐）**：我只填姓名、学校、时间、意向这类。遇到证件号码、紧急联系人，我停下来提示「这一格请你填」，填完继续。这是本次实际采用的模式。

**选 C**：我只做导航和文字录入的提示，不碰任何输入框。

### 9.4 红线

- P0 信息**永不**写入 `confirm-log.md`、简历、Git 仓库
- P0 信息**永不**出现在对话的总结、报告、交付物里
- 用户选 A 之后仍可随时改主意，改的时候立即从 `profile.json` 删除对应字段

## 十、扩充机制

每次投递遇到库里没有的字段，按固定格式追加到对应大类：

```
| 编号 | 字段名 | 必填 | 格式 | 备注 |
```

编号续接，不改已有条目。下次投递自动带上。

**这个库是所有用户共用的公共资产**——某人遇到的新字段，下一个人就不用再卡一次。但库本身不含任何用户的真实信息，只有字段名和格式。

---

## 十一、采集完成的判定

以下三条全部满足，才算问题库跑完：

1. A、B、C、D 四类字段全部有值或明确标注「不适用」
2. P0 / P1 字段的处理方式已由用户明确选定（A/B/C 之一）
3. 用户对整份 `profile.json` 做过一次整体复述确认

第 3 条不能省——单条确认过，不代表整体没矛盾（比如期望城市写了「全国」、籍贯也写了「全国」，就是没改默认值）。
